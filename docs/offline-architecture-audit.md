# NaviSuite Offline Architecture: Project Audit

**Status:** Audit only. No application code, migration or database was changed.
**Date:** 2026-11-19
**Branch audited:** `develop` at `b63bc21`
**Companion document:** [offline-implementation-roadmap.md](offline-implementation-roadmap.md)

---

## 0. Executive summary

The application is a single Laravel 11 monolith with a server-rendered Blade, jQuery and Bootstrap 4 frontend. It has no API, no synchronization code, no queue usage and no globally unique identifiers outside the PMS module. It can run on a vessel, but not as it stands.

Findings that shape the design:

1. **The frontend cannot be separated from the backend cheaply.** 106 Blade views and about 120 jQuery AJAX calls talk to 207 web routes. A desktop client should be a thin shell that loads the onboard server's existing web UI, not a rewrite.
2. **Integer auto-increment keys are used almost everywhere.** A vessel database and the cloud database would generate colliding IDs. Every synchronized table needs a global identity. PMS tables already use UUID keys.
3. **Many writes bypass Eloquent.** Upserts, bulk inserts and query-builder updates are common. Model events therefore cannot reliably capture changes for an outbox. Database triggers can.
4. **Each business area has a clear owner, which makes two-way sync tractable.**
   - Stock is written only by ship roles.
   - PMS execution is ship-side, and PMS approval is office-side.
   - Requisitions pass between ship and office in strict hand-off order.
5. **The workflow state is implicit.** Requisition state is spread across a free-text `orders.status`, `orders.procurement_stage` and about 25 nullable approver columns. Both sides write the same `orders` row, at different stages.
6. **Requisition numbers are generated by counting rows,** with no lock. This is safe offline only if the vessel is the sole author of its requisitions.
7. **The repository root is also the web root.** `bootstrap/app.php` calls `usePublicPath(dirname(__DIR__))`. On the current cPanel deployment, `.env`, SQL dumps, `Archive.zip`, `storage/` and logs may be downloadable over HTTP. This needs checking on the live server now. The vessel server must not repeat this layout.
8. **The frontend loads jQuery, Bootstrap, DataTables, Popper, pdfmake, Font Awesome and Google Fonts from public CDNs.** Pages will break offline until these are served locally.
9. **Laravel 11 is out of security support.** A frozen version deployed to ships that rarely receive updates should start from a supported release. The support dates should be verified.
10. **The test suite exists but is not green.** It has 186 tests, of which 9 fail. Sync work needs a green baseline and MySQL-backed tests.

## 3. Database, models and relationships

### 3.1 Key strategy

| Key type | Tables |
|---|---|
| `INT UNSIGNED AUTO_INCREMENT` (`increments`) | users, roles, vessels and their 5 detail tables, categories, items, orders, order_items, order_approvals, surveys, certificates, vessel_surveys, vessel_certificates, budget_groups |
| `BIGINT AUTO_INCREMENT` (`id()`) | item_groups, vessel_items, item_imports, stock_imports, attachments, all pivots, order_* child tables, service_requisition*, stock_consumptions, stock_movements, ports, currencies, ranks, pms master data, pms_counter_readings, pms_job_intervals, pms_job_checklist_items, pms_required_parts, pms_used_parts |
| **UUID primary key** (`HasUuids`) | **pms_components, pms_job_definitions, pms_jobs** |
| External idempotency key | `cfm_guid` on the 3 PMS tables |
| Natural unique keys | `items.item_key` (SHA1 of article number, group and name), `item_groups (category_id, parent_id, name)`, `vessel_items (vessel_id, item_id)`, `categories.name`/`symbol`, `manufacturers.name`, `ports.unlocode`, `currencies.code`, `ranks.code`, `orders.req_no`, `service_requisitions.req_no`, `vessels.acronym` |

### 3.2 Foreign keys

Legacy 2019 tables use plain `integer` columns with **no FK constraints**. These include `orders.vessel_id`, `order_items.order_id`, `order_approvals.order_id` and `roles.user_id`. Some are signed and some unsigned.

Tables from 2026 use real FKs, many with `ON DELETE CASCADE` or `SET NULL`.

Two consequences for sync:

- **MySQL triggers do not fire for FK cascade actions.** A parent delete must be replicated as a parent delete, and the receiving side's own FK rules reproduce the cascade. Both schemas must therefore have identical FKs.
- The code notes that `orders.id` and `order_approvals.id` have already drifted apart. Code must always match on `order_id`, which it now does.

### 3.3 Deletion conventions

- **Hand-rolled soft delete:** a boolean `status` on most legacy tables, and `ord_status` on `orders`. On `orders`, `ord_status=false` also means "draft".
- **Laravel `SoftDeletes`:** only on `pms_components` and `pms_job_definitions`.
- **Hard deletes exist.**
  - `HomeController@permanentDelete` deletes surveys, certificates, orders, items, categories and vessels from the trash.
  - Draft line items, attachments, PMS readings, parts and master data are also hard-deleted.
- Sync therefore needs tombstones.

### 3.4 Relationship map

Shown as parent, then children.

- **Vessel:** one each of `vessel_particulars`, `framework_descriptions`, `dimensions`, `engines`, `boilers`. Many `roles`, `orders`, `service_requisitions`, `vessel_surveys`, `vessel_certificates`, `vessel_equipment`, `vessel_items`, `stock_*`, `pms_*`.
- **User:** one `role`. The `role` holds `role`, `vessel_id` and `user_type` (`ship`, `srd`, `ssm` or `admin`). There is exactly one role per user.
- **Order:**
  - `order_items`, each with `attachment_order_item` and `order_item_quantity_changes`
  - one `order_approvals`
  - `order_form_parts` (parts A, B and C), each with `order_form_part_edits`
  - `order_procurement_steps`, each with `attachment_order_step`
  - one `order_invoices`
  - `stock_movements` and `stock_consumptions` linked by `order_id`
  - `pms_required_parts.order_id`
- **ServiceRequisition:** `service_requisition_items` (referencing `vessel_equipment` or `vessel_certificates`), one `service_requisition_approvals`, procurement steps with attachments, one invoice.
- **Item** (global catalog): belongs to `categories` and `item_groups` (a tree). Linked to vessels through `vessel_items`, which **also stores the live stock balance**.
- **Stock:** `stock_movements` is the ledger. It references `order`, `order_item`, `stock_consumption` and `stock_import`.
- **PMS:**
  - `pms_components` is a tree with `parent_id`, plus `counter_parent_id` for a shared meter.
  - A component has `pms_counter_readings` and `pms_job_definitions`.
  - A definition has intervals, checklist items, required-part templates and `pms_jobs`.
  - A job has `pms_required_parts` (copied per job) and `pms_used_parts`. Each used part points to a `stock_consumptions` row.
- **Attachment:** one table for all uploaded files. It is linked through 4 pivot tables to order items, order procurement steps, service procurement steps and stock consumptions.

## 4. Authentication and authorization

| Aspect | Finding |
|---|---|
| Guard | Session (`web`) only. File sessions, 120-minute lifetime. |
| API auth | None. No Sanctum or Passport installed. The `.env` has unused Passport placeholders. |
| Login | `laravel/ui` `Auth::routes()`, email and password, bcrypt via the `hashed` cast. |
| Registration | **Enabled.** `Auth::routes()` includes `/register`. A self-registered user has no role, and most pages expect `auth()->user()->role`. This is a security and stability issue. |
| Password reset | Email-based. The SMTP config holds Mailtrap placeholders, so it is effectively not working. It cannot work offline. |
| Roles | A string on `roles.role`. 17 roles are defined in `Role::TYPE_BY_ROLE`: ship roles (`master`, `chief-engineer`, `chief-officer`, `second-engineer`, `operator`), SRD roles, SSM roles, two superintendents and `super-admin`. |
| Authorization style | **No policies, gates or role middleware.** Rules are inline checks in controllers: `abort_unless(in_array($role, ...))`, `Order::hasPendingActionFor()`, and the `InventoryGate`, `PmsAccess` and `PmsAccessGate` helpers. One route middleware, `member`, admits `chief-officer` and `second-engineer` only. |
| Vessel scoping | Ship users are locked to `role.vessel_id`. Fleet-wide shore roles pass `?vessel_id=`. |
| Route protection | Every controller except two declares `auth` in its constructor. `RequisitionController` and `ServiceRequisitionController` sit inside the `member` group, which checks authentication itself. |

**Offline implications:**

- Session login works unchanged on a local server.
- Users and password hashes must be replicated to the vessel for offline login.
- Password reset by email is unavailable offline.
- There is no role middleware to hook. A "vessel mode" guard must be added as new middleware, not as edits to scattered checks.

## 5. Requisition workflows

### 5.1 Item requisition lifecycle (as implemented)

```
SHIP (vessel)                                   OFFICE (cloud)
-------------                                   --------------
Chief Officer / 2nd Eng
  Step 1: Part A form ──► orders row (status=draft, ord_status=0)
  Step 2: details, items (+ per-item attachments)
  Step 3: submit ──► req_no generated, order_approvals row,
                     status='approved by chief-officer'|'... second-engineer'
Master / Chief Engineer
  approve (may edit item_qty, reason, Part A) ──► status='approved by master'
                                                  │
                                                  ▼
                                   GM (SRD) ── delegate ─► DGM/AGM/AM/Supt (SRD)
                                   (Part B)    reviews, returns to GM
                                   GM approves
                                   DGM (SSM) (Part C) assigns to AGM/AM/Supt (SSM)
                                   procurement_stage: administrative_approval →
                                   tendering → bid_evaluation → award_approval →
                                   purchase_order → advance_payment → delivery
                                   SSM officer "Delivery" (sets del_item_qty,
                                   deliver_date, status='delivered')
                                                  │
  ◄───────────────────────────────────────────────┘
Raiser (CO / 2E) confirms receipt (rcv_item_qty) ──► status='received',
  stock credited via StockService::addFromReceipt (+ stock_movements rows),
  procurement step receipt_verification
                                                  │
                                                  ▼
                                   invoice_verification → finance_clearance →
                                   payment → closed (order_invoices)
Technical / Marine Superintendent: sign-off at any stage (and can stand in for a delegate)
Rejection: whoever currently holds it; terminal.
```

### 5.2 Characteristics that matter for sync

- **Hand-off ownership.** `Order::hasPendingActionFor()` decides whose turn it is. At any moment exactly one side holds the requisition. The superintendents' parallel sign-off is the exception.
- **Both sides write the same rows.**
  - `orders.status`, `orders.procurement_stage` and `order_approvals.*` are written by both the ship and the office.
  - On `order_items`, `item_qty` and `rcv_item_qty` are ship-written, while `del_item_qty`, `invoice_qty`, `unit_price` and `line_total` are office-written.
  - Ownership can therefore be expressed per column and per stage.
- **The state is implicit.** It is derived from nullability of about 25 approver and forwarder columns plus a free-text status. Any receiving side must apply the same columns atomically per order, or the derived state is briefly wrong.
- **Requisition numbering.** `RequisitionController::submit()` builds `{ACRONYM}/DK/{CATEGORY}/{count+1}/{year}`. The count covers submitted orders for this vessel and year, with no lock. Two concurrent submits can collide on the unique `req_no`. Offline, this is safe only if the vessel is the only place its requisitions are submitted.
- **Legacy path.** `HomeController@storeOrder` is an older single-step creation route that still exists.
- **PMS integration.** PMS can raise a requisition from a job's required parts through `PmsRequiredPartController@requisition`, which is ship-side.

### 5.3 Service requisitions

The service flow mirrors item requisitions up to GM (SRD), then runs an SRD-owned procurement sequence, with receipt confirmed by the raiser. Confirming receipt of a *Renewal* updates the vessel certificate it refers to. That is a cross-module write on the ship side.

## 6. Inventory: stock transactions and balances

**Model.** Stock is tracked per vessel as ROB (remaining on board).

- `vessel_items.stock_qty` is the live balance. `opening_stock`, `min_qty`, `last_supply_qty` and `last_supply_date` sit on the same row.
- `stock_movements` is an append-only ledger. Each row has a `type` of `opening`, `receipt`, `consumption` or `adjustment`, a signed `qty`, and `balance_after`.
- Every balance change goes through **`App\Services\StockService`**. It updates the balance and writes the ledger row in one transaction.

| Write path | Method | Who | Side |
|---|---|---|---|
| Manual correction or opening balance | `setStock()`, an absolute set that records an adjustment or opening row | Master, and the stock editor roles of their own vessel | Ship |
| Spreadsheet upload | `bulkSet()`, a chunked upsert with bulk movement insert | Ship stock editors | Ship |
| Receipt of a requisition | `addFromReceipt()` | The raiser on receipt confirmation | Ship |
| Consumption (used, damaged, expired, lost, other, PMS job) | `consume()`, which also creates a `stock_consumptions` row and **refuses to go negative** | Chief Officer and Second Engineer; PMS job completion | Ship |
| Ledger backfill | `stock:backfill-movements`, idempotent | Admin CLI | Either |

**Conclusion.** No office role writes stock. The vessel is the single writer of a vessel's stock, provided ship users stop writing to the cloud for that vessel once it has an onboard server. Under that rule, `vessel_items` stock columns and the ledger can be replicated vessel-to-cloud verbatim, with no merge logic.

**Pitfalls:**

- `consume()` validates against the current balance. Inbound sync must **apply ledger rows as facts**, not replay them through `consume()`. Otherwise a stale cloud balance could reject a consumption that really happened.
- `bulkSet()` and the backfill use `DB::table()->upsert()` and `->insert()`. Those writes are invisible to Eloquent events.
- Catalog links (`vessel_items` rows without stock) can be created by office catalog imports for a vessel. These are inserts from the cloud into a table whose stock columns belong to the vessel. Ownership is column-level.

## 7. PMS (planned maintenance)

| Data | Written by | Side |
|---|---|---|
| Master data: ranks, locations, component categories, job types, conditions | super-admin | Cloud |
| Manufacturers | super-admin, CFM import, component edits | Both, keyed by name |
| Component tree, counters, job definitions with intervals, checklist and required-part templates | Ship editors for their own vessel; **super-admin for any vessel** | Mostly ship, sometimes cloud |
| Counter readings (running hours) | Ship editors | Ship |
| Job completion | Ship editors (`PmsJobScheduler::complete()`) | Ship |
| Job approval (`WaitingApproval` to `Completed`) | Office only (`canApprovePmsJobs`) | **Cloud** |
| Next-job generation | Created on completion with a **new UUID**, on whichever server ran the completion | Ship |
| Used parts | On completion, through `StockService::consume()` | Ship |
| Status refresh (`Planned`, `DueSoon`, `Overdue`) | `pms:refresh-jobs` nightly at 00:15, plus on demand | **Both, if both run it** |

**Implications:**

- UUID keys make PMS the easiest module to sync.
- Job generation must happen on exactly one side, the vessel. Otherwise each side creates its own successor job.
- The nightly refresh rewrites `status` on every open job. Running it on both sides would create constant false conflicts. It should run only on the side that owns the vessel's PMS. Its writes can also be treated as derived values that are not sent upstream.
- Office approval and super-admin edits are the only cloud writes into vessel-owned PMS rows. These are the conflict surface.
- `PmsDashboardCache` and `NavCounts` are invalidated only through Eloquent events or explicit `bump()`. A sync applier that writes rows directly must flush them.

## 8. Attachments and file storage

| Files | Storage | Name | Served by |
|---|---|---|---|
| Requisition, procurement and consumption attachments | `local` disk, `storage/app/attachments/{user_id}/{uuid}.{ext}` | UUID | `AttachmentController@view`, behind authentication |
| Certificate copies | `images/cert_copy/` in the project root, so publicly reachable | `time().ext` | Apache directly, **no authentication** |
| User photos and signatures | `images/userphoto/`, `images/signature/` in the project root | `time().ext` | Apache directly, **no authentication** |
| PMS component import uploads | `storage/app/pms-imports` | token | Temporary |
| PDFs and Excel exports | Generated on the fly | none | download |

- The limit is 15 MB per attachment. Allowed types are images, PDF and Office documents.
- `storage/app` is currently 103 MB locally. Most of that is samples and UN/LOCODE data.
- There is no S3 or other cloud disk in use. The `s3` disk is configured but empty.

**Implications:**

- The `attachments` table is a good sync unit: a UUID filename, metadata in the database, and links through pivots.
- **Timestamp filenames will collide** when files from several vessels and the cloud are merged. Two uploads in the same second produce the same name.
- Signature images are needed on the vessel. Print forms show signatories, so shore users' signatures must be sent down.
- Files need their own resumable transfer channel and a "not yet transferred" state in the UI.

| # | Assumption | Where | Why it matters on a vessel |
|---|---|---|---|
| C1 | **The web root is the project root** | `bootstrap/app.php` `usePublicPath(dirname(__DIR__))`, root `index.php`, `.htaccess` | Every file in the project is web-reachable unless the server denies it: `.env`, `*.sql`, `Archive.zip`, `storage/logs/*`, `vendor/`. **Check the live cPanel site now.** The vessel installer must lock this down. |

## 12. Existing synchronization implementation

**None exists.** There is no sync code, no API beyond the stub, no outbox, no change tracking, and no device or node identity.

Existing patterns worth reusing:

- `PmsCfmImporter` is idempotent by external GUID (`cfm_guid`, with deterministic UUIDv5 for split definitions). This is the same idea a sync inbox needs.
- `StockService::backfillMovementsForVessel()` is idempotent by construction and rebuilds a ledger from source events.
- `CatalogService::itemKey()` gives catalog items a deterministic, content-based identity. Both sides can compute it independently.
- The PMS module already uses UUID primary keys.

## 13. Table classification for synchronization

This is a proposal derived from the write-path analysis above. Section 14 lists the decisions it depends on.

| Class | Tables | Direction | Rule |
|---|---|---|---|
| **A. Cloud-owned reference data** | categories, budget_groups, currencies, ports, ranks, surveys, certificates, certificate_categories, pms_locations, pms_component_categories, pms_job_types, pms_conditions | Cloud to vessel | Read-only on the vessel |
| **A'. Cloud-owned, vessel-scoped** | vessels (this vessel only) and its 5 detail tables, users and roles (this vessel's crew plus referenced shore users), user signatures | Cloud to vessel | Read-only on the vessel. Shore users are present for display only, with login disabled. |
| **B. Co-authored catalog** | items, item_groups, manufacturers, vessel_items link rows | Both | Merge by natural key with a deterministic UUID. Inserts never conflict. Updates use last-writer-wins with logging. |
| **C. Vessel-owned operational** | stock_movements, stock_consumptions, attachment_stock_consumption, stock_imports, item_imports, `vessel_items` stock columns, vessel_equipment, pms_components, pms_counter_readings, pms_job_definitions, pms_job_intervals, pms_job_checklist_items, pms_jobs (except approval columns), pms_required_parts, pms_used_parts | Vessel to cloud | Read-only on the cloud for offline-enabled vessels, except for the listed exceptions |
| **C'. Exceptions into class C** | `pms_jobs.status`, `approved_by` and `approved_at` on approval; super-admin edits of PMS trees | Cloud to vessel | Column-level ownership. A conflict is logged if both sides changed. |
| **D. Workflow aggregates** | orders, order_items, order_approvals, order_form_parts, order_form_part_edits, order_item_quantity_changes, order_procurement_steps, order_invoices, attachment_order_item, attachment_order_step; and the service_requisition* equivalents | Both | Ownership follows the stage, applied per column. Conflict detection uses row versions. |
| **E. Co-authored vessel records** | vessel_certificates, vessel_surveys | Both | Pending a business decision. The default is last-writer-wins with a conflict log. |
| **F. Files** | attachments (metadata follows its parent's class), cert_copy, signature and photo files | Follows parent | Separate binary channel |
| **G. Local only** | migrations, password_resets, sessions, cache, jobs, failed_jobs, sync_* tables | None | Never synchronized |

## 14. Risks

| # | Risk | Likelihood | Impact | Mitigation in roadmap |
|---|---|---|---|---|
| R1 | Ship users keep writing to the cloud for a vessel that has an onboard server. This causes stock divergence and `req_no` collisions. | High without a guard | High | Cloud-side write lock for ship roles on offline-enabled vessels |
| R2 | Writes that bypass Eloquent are missed by change capture | Certain with model events | High | Trigger-based capture |
| R3 | Schema drift between cloud and vessels caused by manual SQL and different release versions | Medium | High | Schema version in the sync handshake. Refuse to sync on mismatch. Automated migrations on vessels. |
| R4 | Shared hosting forbids `CREATE TRIGGER`, long requests or large uploads | Unknown | High | Confirm hosting. Move the cloud to a VPS if needed. |
| R5 | Implicit requisition state is applied partially, so derived state is wrong | Medium | Medium | Apply each order aggregate in one transaction |
| R6 | Office approves a PMS job while the vessel edits or cancels it | Low | Low | Column ownership plus a conflict log |
| R7 | Clock skew on vessel PCs | High | Medium | Sequence-based ordering. Skew is detected and reported at handshake. |
| R8 | Vessel restored from an old backup re-sends or loses changes | Medium | High | Node generation counter and re-baseline from the cloud |
| R9 | Expensive or slow satellite links | High | Medium | Compression, delta payloads, files sent last, bandwidth caps |
| R10 | Public exposure of `.env`, dumps and logs on the current cloud host | Unknown | **Critical** | Verify immediately, independent of this project |
| R11 | Laravel 11 is out of security support on a fleet that is hard to patch | Certain | Medium | Upgrade before the first vessel release |
| R12 | No green test baseline (9 failing), no MySQL-backed tests | Certain | Medium | Fix first. Add a MySQL-backed sync test suite. |
| R13 | Master PC sleeps, updates or reboots unexpectedly | High | Medium | Installer sets the power plan, update restart policy and service recovery |
| R14 | Self-registration creates role-less accounts | Medium | Medium | Disable `/register` |

## 15. Open questions for the business

The roadmap states the assumption used for each question until it is answered.

1. **Single author per vessel.** Once a vessel has an onboard server, may its crew still log in to the cloud and create requisitions, consumptions or PMS records for that vessel? *Assumed: no. The cloud is read-only for that vessel's ship roles.*
2. **Office edits to vessel-owned data.** May super-admin keep editing a commissioned vessel's PMS tree, equipment list or stock? *Assumed: PMS approval only. Other edits are routed through the vessel or treated as conflicts.*
3. **Certificates and surveys.** Who is authoritative for `vessel_certificates` and `vessel_surveys`, ship or office? *Assumed: both, last-writer-wins with conflict review.*
4. **Password changes.** May crew change their password on the onboard server? *Assumed: yes. The change is sent to the cloud, and the newest change wins.*
5. **Shore users onboard.** Should a visiting superintendent be able to log in to a vessel server? *Assumed: no, apart from one designated support account per vessel.*
6. **Connectivity.** What link types are used (VSAT, Fleet Broadband, Starlink, port Wi-Fi)? What are the typical bandwidth and data costs? Should sync run automatically, on a schedule, or only when the crew triggers it?
7. **Hardware and OS.** Which Windows editions and versions run on board? Is it Windows 10 22H2 or later, Pro or Home? How many client PCs per vessel? Is the master PC a dedicated machine?
8. **Production MySQL.** What version is it? Is the cloud on shared cPanel hosting, and does the database user have the `TRIGGER` privilege? Can `schedule:run` cron be set?
9. **Catalog scope.** Does a vessel need only its own linked catalog items, or the whole fleet catalog?
10. **Attachment scope.** Should office procurement documents (quotes, POs, invoices) go down to vessels? Is there a maximum size for files sent over satellite?
11. **Software updates.** How should new versions reach vessels: over the sync link, by USB, or by technician visit?
12. **Requisition numbering.** Is the vessel-generated `req_no` final? Are there in-flight drafts on the cloud that must be migrated at commissioning?
13. **"HTTP APIs" for clients.** Is a desktop client that loads the onboard server's existing web UI over HTTP(S) acceptable? The alternative is a new client built against JSON APIs.
14. **Backups.** Is there an external disk, NAS or USB medium available onboard? Who is responsible for checking backups?
15. **Fleet size.** How many vessels, and how fast will they be onboarded?
